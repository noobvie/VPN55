# Internationalisation — VI (default) · EN · FR

Phase 7. This document is the whole i18n contract: what is translated, what is
deliberately not, where each kind of string lives, and which of the rules are
enforced by a machine rather than by memory.

**Vietnamese is the default locale.** English is the fallback and the
key-authoring source. French is the third. `vi.json` and every `vi.txt` is the
file that must never have a missing key — it is what most users see.

---

## 1. What is translated

| Surface | Translated | Where the strings live |
|---|---|---|
| Admin panel | yes | `panel/locales/{vi,en,fr}.json` |
| Self-serve portal (Phase 8) | yes | the same catalogs |
| Client-config setup instructions | yes | `lib/locales/<tag>/{vi,en,fr}.txt` |
| Client-config comment headers | yes | the same files |
| nginx's 502/503/504 page | **all three at once** | `deploy/nginx/vpn55-offline.html` |
| `site/index.html` | Vietnamese only | inline, by design — it is the landing page |
| `vpn55.sh` and every menu | **no** | English, in the source |
| `error()` / `warn()` in `lib/` | **no** | English, in the source |
| `helper/vpnctl` | **no** | English, in the source |

The offline page is the one surface that cannot use a catalog: nginx serves it
exactly when the process owning `panel/locales/` is the thing that is down, so
there is no negotiation available and no `t()` to call. It therefore carries
Vietnamese, English and French stacked on one page. Before it existed, a
Vietnamese user whose portal was restarting got nginx's built-in English
`502 Bad Gateway`.

The installer stays English because its audience is an operator with root on a
Linux box, and translating a root installer multiplies the test surface for no
reach. That is a decision from the build plan, not an omission.

The files the installer *hands over* are a different audience entirely — they are
read by the person who will use the VPN — so those are translated. The installer
asks, once per delivery, which language to write them in, and takes
`VPN55_ARTIFACT_LOCALE` instead when it is set.

## 2. Keyed catalogs, never phrase maps

`t('service.state.running')` against the catalogs. Never a map keyed on English
strings.

This is not a style preference. A phrase map keyed on English word order misses
every translator who reorders the sentence, and the failure is invisible because
the two maps look parallel and byte-count identical. A sibling project shipped 27
unbranded strings that way — the page title and a currency label among them —
with both maps "verified".

The same rule applies to the shell side, where the catalogs are text rather than
JSON: a section is looked up by its **name**, never by matching its English body.

## 3. The two halves

### The panel — JSON catalogs

```
panel/locales/{vi,en,fr}.json     flat dotted keys
panel/lib/i18n.js                 load, negotiate, t(), fallback + log
panel/public/js/i18n.js           the browser half: t(), tOr(), apply()
panel/public/js/format.js         Intl — bytes, numbers, dates, durations
```

The catalog for the negotiated locale is **inlined into the shell page**, so the
first paint is already in the viewer's language. Fetching it afterwards would
show a flash of key names, which is the hardcoded-English problem wearing a
different hat.

A missing key falls back to English **and logs once**. A key missing from English
too returns **the key itself, visibly**. A blank would read as a design decision
and would never be reported.

### The adapters — text catalogs

```
lib/locales/<adapter tag>/{vi,en,fr}.txt
lib/core_i18n.sh                  i18n_resolve, i18n_render, i18n_render_comments
```

Sections are introduced by `@@ name` and carry `{placeholder}` tokens filled from
the caller's `name=value` pairs. Substitution is bash parameter expansion over one
string — no `sed`, no `eval` — because a value here can be a passphrase or a
server address and both can hold characters a regex engine or a shell would read
as syntax.

Every adapter's `client_config` verb takes the locale as its **third positional
argument**:

```
vpn_<proto>_client_config  <cred_id> [artifact] [locale]
```

That reaches the adapter from a caller which does not know which protocol it is
talking to, and that is correct: **a language tag is not protocol vocabulary.**
The contract did not need widening for it.

## 4. Rendering happens at handover, not at issue

The instructions are prose for whoever receives the credential, and **nobody
knows at issue time which of the three languages that person reads** — the
operator issuing it and the person receiving it are usually not the same person,
which is the whole reason the self-serve portal exists.

So the adapters spool the **facts**, not one rendered language:

| Adapter | Spooled | Rendered on demand |
|---|---|---|
| WireGuard | the config body (holds the private key) | the whole instructions page |
| OpenVPN | `<cred>.meta` — cred, user, tunnel address | the whole instructions page |
| IKEv2 | `<cred>.meta` — user; `<cred>.pass` — passphrase | the whole instructions page |

Every locale then comes out of one spool entry, on the same TTL as the artifact
it describes, so the artifact list stays honest about what is left. Freezing one
language into a file that lives for hours and is fetched by somebody else would
make the credential's language a property of who issued it.

**Prose is its own artifact, never a header inside another one.** All three
adapters ship the configuration and the instructions as two separate artifacts.
WireGuard used to put its prose in a comment header inside the `.conf`, and that
was wrong in a way the i18n rules alone do not catch: the config is the one
artifact in this project offered as a QR code, and prose makes its length a
property of the locale — which is chosen at handover, by a caller the adapter
cannot ask. The adapter was promising `qr 1` about a payload it could not
measure, and in Vietnamese with obfuscation on it was three times the size that
scans. Keep prose out of anything a camera has to read.

`i18n_render_comments` is therefore currently unused. It is kept because a future
adapter may have a config format where a comment header is the right place for
something short — not as an invitation to put a page of prose back.

## 5. Formatting is Intl, in the browser

Dates, numbers, byte sizes and relative times are formatted in
`panel/public/js/format.js`, which is the only place that knows the viewer's
locale **and time zone**. `panel/lib/view.js` sends raw values on purpose: every
number leaves as a number and every instant as a Unix epoch. A value formatted on
the server arrives pre-translated into the wrong language and cannot be
un-formatted.

**There is no `+ 's'` anywhere in this codebase.** Vietnamese has no plural
inflection at all and French pluralises differently from English, so hand-rolled
plural logic is wrong in two of the three locales. Where a count needs a word,
the catalog carries a phrasing that works for any count in that language, and
`Intl.NumberFormat` renders the number. Relative times go through
`Intl.RelativeTimeFormat`, which does the grammar in every locale.

Two things are deliberately **not** localised: the IEC unit symbols (`KiB`,
`MiB`, `GiB` are the same in every language; "translating" them would be
inventing a unit) and the em dash that stands for *no reading*.

### The two spaces that are not U+0020

`format.js` builds a duration by concatenating a number onto a catalog string —
`numeric(d) + t('unit.days.short')` — so the gap between them, where a language
wants one, lives in the catalog value:

| | `unit.days.short` | renders |
|---|---|---|
| en | `d` | `3d 4h` |
| vi | `<NBSP>ngày` | `3 ngày 4 giờ` |
| fr | `<NBSP>j` | `3 j 4 h` |

Those leading spaces are **U+00A0**, not U+0020. A breaking space there lets a
narrow column wrap `3` onto one line and `ngày` onto the next, which reads as a
rendering fault. English needs no space at all and gets none.

French additionally sets a **no-break space before `:` `;` `!` `?` and inside
`« »`** — U+202F, the narrow one. `fr.json` had 51 of these as plain U+0020,
which permits a wrap that leaves a colon opening a line, and French is the +17%
locale so it is the one that wraps. `lib/locales/*/fr.txt` deliberately does
**not** get this treatment: those are fixed-width plain-text artifacts that never
re-flow, so there is no wrap to prevent, and U+202F risks a tofu box in a basic
text viewer where U+0020 is safe.

## 6. Vietnamese diacritics and the font stack

Vietnamese stacks two marks on one vowel — ế ộ ữ ậ ề ợ — and those live in
**Latin Extended Additional (U+1EA0–U+1EF9)**, a block plenty of respectable
faces do not carry. A browser does not fail on a missing glyph: it substitutes
**per character**, so a word renders half in the chosen face and half in whatever
the system picks. It reads as a fault on the reader's machine rather than a fault
in the page, which is exactly why it survives review.

Two of the vendored theme's four stacks had that hole, and neither is visible on
a Windows development machine:

| Theme | Vendored stack | What breaks |
|---|---|---|
| `matrix` | `'Courier New', Courier, monospace` | a macOS or Linux reader without Windows-vintage Courier New lands on **Courier**, which has no Latin Extended Additional |
| `anime` | `'Segoe UI', 'Helvetica Neue', Arial, sans-serif` | Segoe UI is Windows-only, so a macOS reader lands on **Helvetica Neue**, whose coverage is incomplete |

⚠ **The check reads four files, and the list is the whole guarantee.** It was
three panel stylesheets, and `site/index.html` — the only page in this repo that
is entirely Vietnamese — shipped naming `"Helvetica Neue"` for exactly as long,
because the rule was enforced everywhere except the page with the most
Vietnamese on it. `site/index.html` and `deploy/nginx/vpn55-offline.html` are now
in `CSS` in the script, and because those two name their tokens `--sans` and
`--mono` rather than `--font`, the property pattern lists all four names. A new
surface that invents a fifth adds it there.

`vendor/office-tools.css` is a pinned copy and is never edited, so the fix is in
`panel.css`, which loads second: `--font` is redefined for `:root` and for every
`[data-theme]` the vendored file defines it in. Each theme keeps its character —
matrix is still monospaced, anime is still a soft humanist sans — but every stack
now names a face **measured** to carry the whole repertoire before it reaches
anything that does not.

### Measured, not assumed

```
node .github/scripts/check-fonts.mjs --probe C:/Windows/Fonts
```

parses each font file's `cmap` and reports coverage of the 142-code-point
Vietnamese repertoire. Windows 11 (build 26200), 2026-08-30:

| Family | Coverage |
|---|---|
| Segoe UI, Arial, Consolas, Courier New, Tahoma, Calibri, Times New Roman | **full**, 142/142 |
| Verdana | 141/142 — no U+031B combining horn |

The Apple and Linux rows in the script's table are marked as *reasoned*, not
measured, and the check treats them as **unverified**: a stack may name them, but
it may not rely on them.

The check, run without arguments, refuses any stack that names a family known to
lack the block — **anywhere in the stack, not merely in front of the verified
one**. Being listed after a covering family only protects a reader on a platform
where that covering family exists, and these stacks are built from
platform-specific names.

## 7. String expansion — lay out against the longest locale

Measured across the whole catalog (`check-expansion.mjs`, placeholders excluded).
**Do not quote these from memory — run the script.** The figures below went stale
by a factor of 2.4 once the settings, alerts and portal sections landed, and a
stale ceiling table is worse than none: it is a number somebody lays out against.

```
vi   16999   +0% vs en
en   16973   (base)
fr   19774   +17% vs en
```

French lands squarely in the 15–25% band the plan predicted. Vietnamese is now
level with English overall rather than above it — the aggregate moves as sections
are added and it is not the number that matters. Of the **124 strings that sit in
a box which cannot wrap** — table headers (`.grid th` is `white-space: nowrap`),
badges, buttons, tabs — the longest rendering is:

```
fr    60
vi    49
en    15
```

**English is never the longest one for anything that matters.** Laying out
against it is laying out against the wrong language. The layout follows: labels
wrap, table columns are content-sized, buttons are padded rather than measured,
and wide tables scroll inside their own box so the page body never scrolls
sideways.

The check enforces a character ceiling per class (26 for a column header, 22 for
a badge, 30 for a button or tab) so nobody lands a forty-character caption in one
language and finds out from a screenshot months later.

## 8. UTF-8, end to end

| Hop | How |
|---|---|
| Catalog files | UTF-8, LF, no BOM |
| Panel → browser | express labels HTML, JSON, CSS and JS `; charset=utf-8`; the page also carries `<meta charset="utf-8">` |
| nginx | passes the proxied charset through untouched; `charset utf-8;` covers the responses **nginx itself** generates — a 502 when the panel is down, a 413 on an oversized body |
| Panel → adapters | `spawn` with `LC_ALL=C` pinned in a fixed env |
| Adapters → panel | `Buffer.toString('utf8')` on both pipes |
| Files bash writes | `fs_write_atomic`, byte-exact; read back with `readFileSync(…, 'utf8')` |

`LC_ALL=C` looks like the wrong answer and is the right one. **C is the
byte-transparent locale**: it makes no character-class or collation decisions, so
UTF-8 in a child's output arrives as exactly the bytes it left as. It is pinned
rather than inherited because inheriting makes the child's behaviour depend on
how the systemd unit happened to be started, which is not a thing anyone will
think to check. Not `C.UTF-8`, which is absent on musl and older glibc — a locale
that does not exist is a warning on stderr from every tool that notices.

### User names stay ASCII, on purpose

`users_validate_name` is `^[a-z][a-z0-9_-]{1,31}$`. That is **not** an i18n gap to
be closed by widening the regex. A user name here becomes a filename, a
certificate subject, a peer comment in a server config, and an argv word passed
to a root helper. It is an identifier, not a display string.

If a Vietnamese display name is ever wanted, it belongs in a separate
`display_name` field carried as data and never used as a key — that is a registry
change with its own review, not a translation.

## 9. Locale choice

Cookie (`vpn55_locale`) → `Accept-Language` → the configured default.
**Never geography.** Where someone is standing is not what language they read,
and a Vietnamese speaker on a business trip does not want the panel in German.

The cookie is `SameSite=Lax` — following a link into the panel should arrive in
the language the person chose, and a locale is not a credential — with `Secure`
set when the page is HTTPS, matching what the session cookie does.

**Per browser, not per account.** Storing it on the admin record would mean the
panel process writing `admins.json`, and the panel process may not write anything:
every write goes through `helper/vpnctl`'s seven verbs, and adding an eighth is a
security-model change (`docs/security-model.md` §3), not a convenience. A display
preference does not justify widening the privileged surface. The switch is
instant and the cookie lasts a year, so the cost is one click on a new machine.

## 10. What CI enforces

Five checks, in the `locales` job:

| Script | Refuses |
|---|---|
| `check-locales.mjs` | key sets that diverge across `vi/en/fr`; a blank value; a catalog that does not parse |
| `check-i18n-usage.mjs` | a key the panel **looks up** that exists in no catalog |
| `check-locale-text.mjs` | a missing `lib/locales` file or section; a **dropped placeholder** |
| `check-fonts.mjs` | a font stack that leans on a family known to lack Vietnamese; a vendored `--font` that `panel.css` fails to override |
| `check-expansion.mjs` | a laid-out string past its ceiling in **any** locale |

`check-i18n-usage.mjs` exists because key parity cannot see the other direction.
All three catalogs can agree perfectly while the panel asks for a key nobody ever
authored — and that is what it found on its first run: `panel/lib/auth.js` audited
`auth.signed_in` and `auth.signed_out` while the catalogs carried `auth.signedin`
and `auth.signout`. Nobody had noticed because the audit view that renders them
is not built yet, which is exactly the kind of gap that ships: the bug was already
written and simply not on screen this month.

⚠ **A prefix claim only counts when the literal is inside the call.** The pattern
is `t('some.prefix.' + …)` — the string has to be the first thing after the
paren. `alerts.js` had `const base = 'alert.' + payload.type` on its own line,
with a comment stating that this let the checker see the claim; it never matched,
and all sixteen live `alert.*` keys sat in the "never looked up" list for as long
as the comment did. That list is only useful while it is short, so anything that
pads it with live keys is hiding the dead one it exists to surface.

## 10a. An error string names the next step

Every message a person can be shown when something failed says **what happened
and what to do about it**. "That did not work." is not a message; it is the
absence of one, and it was the catch-all behind every `tOr(err.error,
'portal.failed')` on the surface read by someone who is already stuck.

The bar is lower for a code only a tampered or stale client can trigger —
`cred.invalid_id`, `settings.unknown_key`, `portal.artifact_unknown` — because no
confused human reaches those. It is highest on the portal, whose reader has no
shell, no journal and no second window.

Confirmations carry the matching obligation: name the consequence and say whether
it can be undone. `cred.revoke.confirm` — *"It cannot be restored, and that person
will need a new credential"* — is the shape.

`check-locale-text.mjs` catches the failure with no JSON equivalent. A translator
who drops `{endpoint}` has removed the server address from a page whose entire
purpose is to carry it — and the sentence still reads perfectly.

## 11. Adding a fourth locale

1. Add the tag to `VPN55_LOCALES` in `lib/core_i18n.sh`, to `LOCALES` in
   `.github/scripts/check-locales.mjs` and `check-locale-text.mjs`, and to
   `locales=` in `deploy/panel.conf.example`.
2. Copy `panel/locales/en.json` and translate the values. Do not reorder or
   rename a key — the key is the contract, the English text is not.
3. Copy each `lib/locales/<tag>/en.txt`. Keep every `@@ section` name and every
   `{placeholder}` exactly as it is; translate only the prose around them. Code
   blocks (the PowerShell in the IKEv2 page) are **not** prose — translate the
   comments inside them, never the commands.
4. Add `locale.name.<tag>` to all catalogs, so the language picker can name it.
5. Check the font stacks cover the new script:
   `node .github/scripts/check-fonts.mjs --probe <font directory>`. If the script
   needs a face the current stacks do not name, that is a `panel.css` change and a
   new row in the coverage table, with the measurement that justifies it.
6. Run all five checks. Do not ship a locale on the strength of it looking
   parallel — that is exactly what looked fine in the project that shipped 27
   unbranded strings.
