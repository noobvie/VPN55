Check the locale catalogs and translated surface. Scope: $ARGUMENTS, or all of
`panel/locales/`, `lib/locales/` and every `t()` / `i18n_render` call site if none
given.

VI is the default and what most users see. EN is the fallback **and** the
key-authoring source language. FR is the layout worst case.

The full contract is `docs/i18n.md`. Read it before reporting anything as a
defect — several things that look like gaps are settled decisions with reasons.

## 1. Mechanical — run all five, report actual output

```bash
node .github/scripts/check-locales.mjs        # key parity across vi/en/fr
node .github/scripts/check-i18n-usage.mjs     # every key the panel asks for exists
node .github/scripts/check-locale-text.mjs    # lib/locales sections + placeholders
node .github/scripts/check-fonts.mjs          # stacks carry Vietnamese
node .github/scripts/check-expansion.mjs      # nothing past its ceiling
```

These are what CI runs. Run them before reading anything, and report what they
actually printed rather than what they usually print.

`check-i18n-usage.mjs` prints two NOTES that are not failures — lookups whose key
it cannot read, and catalog keys nothing looks up yet. The second list is expected
while the audit and enforcement views are unwritten. It is also what a renamed key
leaves behind, so read it rather than skipping it.

Then the part no script covers:

- **No phrase map.** Any object keyed on an English sentence is the failure this
  project exists to avoid: a map keyed on English word order misses every translator
  who reorders the sentence, and two byte-identical maps feel like proof and prove
  nothing. Keys are stable identifiers.
- **Two catalog locations, and only two.** `panel/locales/*.json` for the panel;
  `lib/locales/<tag>/<locale>.txt` for the text the adapters hand an end user. That
  is a different FORMAT for a different consumer — bash cannot parse JSON without a
  dependency — not a second copy of the same strings. A third is a defect.

## 2. Quality of the strings

- A missing key falls back to English **and logs**. A silent blank is worse than an
  untranslated string — check the fallback path actually logs.
- Dates, numbers, byte sizes and relative times go through `Intl`, **in the browser**
  (`panel/public/js/format.js`), because that is the only place that knows the
  viewer's time zone. `panel/lib/view.js` sends raw numbers and Unix epochs on
  purpose; a value formatted server-side arrives in the wrong language and cannot be
  un-formatted. Vietnamese has no plural inflection and French pluralises differently
  from English — any hand-rolled `+ 's'` or `count === 1 ? … : …` is a bug in two
  locales.
- No sentence assembled from fragments. Concatenating `t('a') + name + t('b')` fixes
  English word order onto every language; pass the value as a parameter into one key.
- Units (`KiB`/`MiB`/`GiB` are IEC symbols), protocol names and product names stay
  untranslated; **UI nouns around them do not** — check a sample of VI strings for
  English left in place.
- In `lib/locales/`, **commands are not prose.** The IKEv2 page carries a PowerShell
  block: the `#` comments inside it are translated, the cmdlets and parameter names
  are not.

## 3. Layout and rendering

- Lay out against the **longest** locale. `check-expansion.mjs` prints which that is
  per class — currently FR for 42 of the 84 laid-out strings, VI for 32, EN for 10.
  Sizing to English is sizing to the wrong language.
- The font stack renders Vietnamese stacked diacritics (ế, ộ, ữ) without falling back
  mid-word. `panel.css` overrides `--font` for every theme because two vendored
  stacks had that hole; if an override is dropped the check fails. Re-derive coverage
  with `check-fonts.mjs --probe <font dir>` — measure, never look.
- UTF-8 end to end. `LC_ALL=C` is pinned in both `spawn` envs deliberately: C is the
  byte-transparent locale. Do not "fix" it to `C.UTF-8` — that locale is absent on
  musl and older glibc.
- Locale persists **per browser** (cookie `vpn55_locale`) and defaults from
  `Accept-Language`. **Never geolocated.** Not per account, on purpose: the panel
  process may not write `admins.json`.
- **User names are ASCII on purpose** (`^[a-z][a-z0-9_-]{1,31}$`). That is an
  identifier reaching a root helper, not a display string. Do not report it as an
  i18n gap and do not widen the regex.

## 4. Out of scope on purpose

The bash installer is **English-only** — `vpn55.sh`, every menu, every `error()`
and `warn()` in `lib/`, and `helper/vpnctl`. Operators are technical and translating
a root installer multiplies the test surface for no reach.

**But the files the installer HANDS OVER are translated**, and that is not a leak:
`lib/core_i18n.sh` and the `i18n_render` calls inside `lib/proto_*.sh` are the
Phase 7 design, not something that crept in. The line is *who reads the string* —
an operator with root, or the person who will use the VPN.

So flag a `t()` or a catalog lookup that renders an OPERATOR-facing string, and
leave the end-user artifacts alone.

Report missing/orphan keys as two explicit lists, then quality findings with
`file:line`.
